# 계획: 기준 데이터 + 계속 배우는 판단 규칙 (2026-11-07 정함)

## 사용자가 정한 것
- 비교용 숫자의 기준 티어: **에메랄드 ~ 다이아** (1차 목표 바로 위)
- 롤 지식(판단 규칙)은 **최상위 티어**에서 그대로 배워요. 플래티넘에 따른 시사점이 있을 때만 따로 적어요.
- 챔피언: **원딜 4개** (징크스, 애쉬, 미스포츠, 자야)
- 통계 사이트 숫자: 필요한 것만 필요한 만큼 인용해요. 리포트에 출처는 적지 않아요. 성장 지표는 직접 계산해요.
- 유튜브 강의: 제가 **규칙 후보**를 만들고, 사용자가 보고 골라서 확정해요(바로 넣지 않음).
- 영상 고르기: 제가 웹 검색으로 최상위 티어 원딜 강의 후보를 주제별로 찾아 드리고, 사용자가 골라요.
- 자막 가져오기: 제 작업 공간에서는 유튜브 접속이 막혀 있어서 사용자가 자막을 붙여 넣어요. 긴 영상은 필요한 구간만 붙여 넣어도 돼요.
- 처음 양: 원딜 공통 주제(라인전, 의미 없는 죽음 줄이기, 오브젝트 전 준비, 한타 위치) 5~10개 → 징크스 전용 몇 개. 영상 하나에서 출처 시간 위치를 붙인 후보 3~8개 정도를 뽑아요. 그 뒤로는 리포트에서 반복되는 실수 주제 위주로 더 찾아요.
- 모든 자료는 이 GitHub 저장소에서 관리해요. PC에 있던 작업 파일은 11-07에 저장소로 옮겼어요.
- 새 기능은 먼저 넣어 보고 사용자에게 어떤지 물어봐요. 필요한 것만 남겨요.

## 1단계: 작업 파일을 저장소로 옮기기 (11-07 끝남)
- 옮긴 위치와 실행 방법은 `tools/README.md`에 있어요. 옮긴 뒤 만든 리포트와 분석 결과가 옮기기 전과 똑같은지 확인했어요.
- `tools/report/`(build2.py, report.css), `tools/analyze.py`, `tools/inline_img.py`, `tools/make_gray_map.py`, `mockup/` 피드백 파일, `data/` Data Dragon 파일과 흑백 지도.
- 글꼴(woff2 2개)은 저장소에 넣어도 돼요(Pretendard, Archivo 모두 OFL).
- 기록 프로그램은 `logger.py`, 배치 파일만 넣어요. `config.json`은 넣지 않아요.
- 넣은 뒤 PC 폴더는 백업으로만 둬요.

## 2단계: 기준 데이터 모으기 (GitHub Actions) — 11-07 도구 완성, 첫 실행 기다리는 중
- 만든 것: `scripts/benchmarks.py`, 워크플로 "기준 데이터 모으기"(`.github/workflows/benchmarks.yml`). 저장소 원본 경기 4판으로 뽑기 시험, 가짜 응답으로 수집 흐름 시험을 마쳤어요. 실제 Riot API로는 아직 안 돌려 봤어요.
- 계획과 달라진 점: 요약만 저장하면 다음 실행 때 판 수를 늘릴 수 없어서, 한 판에서 뽑은 숫자 한 줄(약 400바이트)을 `benchmarks/rows/<챔피언>.jsonl`에 같이 쌓아요. 원본 경기는 여전히 저장하지 않아요. 참가자 식별값은 짧은 해시로만 저장해요(한 사람이 한 챔피언으로 3판 넘게 들어가지 않게 하려고).
- 패치: 기본은 최신 패치만 모아요. 요약은 최신 패치 판이 60판보다 적으면 바로 전 패치까지 합쳐요(최대 3개).
- 보여 줄 최소 판 수: 숫자 30판, 상성 10판, 빌드 10판(`minN`).
- 새 워크플로 "기준 데이터 모으기"(손으로 실행). Secret `RIOT_API_KEY`를 써요.
- 순서: league-v4로 KR 솔로 랭크 에메랄드/다이아 참가자 목록 → 최근 솔로 랭크 경기 ID → 원딜 4개 챔피언이 원딜로 나온 경기만 match + timeline 받기 → 요약 계산.
- 요청 제한(개인 키는 2분에 100번 정도)을 지키고, 몇 판까지 모을지는 입력값으로 정해요. 챔피언당 처음에는 100~200판 정도로 시작해요.
- 원본 경기는 저장소에 쌓지 않고(용량), 요약만 `benchmarks/<챔피언>.json`에 저장해요.
- 요약 내용(평균, 중앙값, 상위 25%/75%):
  - A. 10분/15분 CS, 골드, 경험치, 분당 피해, 시야 점수
  - B. 첫 코어/두 번째 코어 아이템 완성 시간
  - C. 상대 원딜별 15분 골드 차이(판 수가 충분한 상성만)
  - D. 많이 쓰는 빌드/룬 순위
  - 서폿이 바텀에 있던 비율, 서폿 있을 때/없을 때 CS(이미 만든 규칙과 같은 계산)
- 주의: 판 수가 적으면 숫자가 흔들려요. 각 숫자 옆에 판 수를 같이 저장하고, 기준보다 적으면 리포트에 보여 주지 않아요.

## 3단계: 리포트에 넣기 — 11-07 analyze.py 쪽 완성
- `analyze.py` 결과에 `benchmark` 칸이 생겼어요(원딜 판만). 기준 데이터가 없으면 `available: false`예요. 리포트(`build2.py`) 화면은 실제 기준 데이터가 들어온 뒤에 만들어요.
- `analyze.py`가 그 판 챔피언의 요약 파일을 읽어서 "기준 대비" 값을 계산해요.
- 리포트에는 A~D를 넣어 보고, 사용자에게 어떤지 물어봐요.
- 나중에 할 것: 죽음마다 승률이 얼마나 깎였는지(승률 모델이 필요해서 뒤로 미룸).

## 4단계: 계속 배우는 판단 규칙
- `knowledge/rules.md`: 규칙 하나마다 내용, 근거(어느 판/어느 강의), 지지 횟수, 마지막 확인 패치를 적어요. 플래티넘 시사점은 있을 때만 적어요.
- 패치가 바뀌면 챔피언/아이템 관련 규칙에 "확인 필요"를 표시해요.
- `knowledge/candidates.md`: 강의나 피드백에서 나온 규칙 후보. 사용자가 고르면 rules.md로 옮겨요.
- `knowledge/champions/<챔피언>.md`: 챔피언별 메모. 그 챔피언 판에서만 읽어요.
- `me/patterns.md`: 여러 판에서 반복되는 습관, 다음 판 목표를 지켰는지 기록.
- 한 판마다 하는 순서: 분석 → 피드백 → 사용자 확인/반박 → 규칙 갱신.
- 지금까지 정한 판단 규칙(서폿 로밍, 바텀 원딜 킬, 스펠 칸 등)은 1단계에서 rules.md로 옮겼어요.

## 11-07 밤에 정한 것: React로 다시 만들기 + 리포트 빨리 받기
- **화면은 React로 다시 만들어요.** 화면이 적은 지금 바꾸는 게 가장 싸서 바로 시작해요.
- 구조: 파이썬은 데이터만 만들어요(분석 → 판별 리포트 데이터 JSON). React 화면은 사이트가 열릴 때 그 JSON을 읽어서 그려요. 그래서 새 판이 들어와도 React를 다시 빌드하지 않아요. 빌드는 화면 코드가 바뀔 때만 해요.
- 첫 단계는 `build2.py`에서 계산 부분을 떼어 내서 리포트 데이터 JSON으로 만드는 거예요. 디자인 값은 `report.css`(v4)에서 가져와요.
- artifact로 올리는 한 파일짜리 리포트도 React 빌드에서 만들 수 있게 해요.
- **목표 시간:** 게임이 끝나고 리포트를 받기까지 5분 안이면 쓸 만하고, 10분을 넘으면 너무 느린 거예요. 줄일 수 없는 부분은 Riot이 경기 데이터를 공개하기까지 걸리는 시간(보통 몇 분)이에요.
- 피드백 시간과 토큰 줄이기에서 쓰기로 한 것:
  1. 판마다 새 대화에서 피드백을 써요(긴 대화는 답할 때마다 앞 내용을 다시 읽어서 토큰이 몇 배 들어요).
  2. 숫자로 판단할 수 있는 규칙은 `analyze.py`가 미리 판단해서, 피드백용 짧은 요약(걸린 규칙 목록 포함)을 만들어요. 피드백을 쓸 때는 이 요약만 읽어요.
  4. 리포트 만들기와 올리기는 워크플로가 자동으로 해요. 대화에서는 피드백 파일만 써서 올려요.
  - 쓰지 않기로 한 것: 피드백 글 길이 제한, 더 가벼운 모델로 바꾸기.
- 아직 안 정한 것: 피드백 글을 대화에서 쓸지(숫자 리포트를 먼저 받고 글은 나중), 워크플로에서 Anthropic API로 자동으로 쓸지(판마다 따로 요금이 듦).
- 확인할 것: PC 기록 프로그램이 게임이 끝나자마자 워크플로를 실행하게 하려면, 프로그램에 든 GitHub 토큰에 워크플로 실행 권한이 있어야 해요. 아직 확인하지 않았어요.
